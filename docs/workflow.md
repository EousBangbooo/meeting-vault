# 工作流

## 复制后看哪里

macOS 监听器将匹配的转写保存到 `inbox/`，通知你打开会议库根目录的 `会议处理.html`。顶部数字按入箱的转写文件计数，区分未启动、等结果、待确认、判断有分歧和已处理。文件变化后可点「刷新」。监听器运行期间，有待处理会议时每天发一次提醒。已经装过旧版监听器的用户需要重新运行 `./bin/install.sh`。

## 谁来判断

由你指定的 AI 或人工负责。展开一场未启动的会议，点「复制审阅指令」，发给在 Meeting Vault 仓库里运行、能读取本地文件的 AI。它会按[单场会议审阅](review-guide.md)登记接单和保存判断。保存时，脚本核对候选里的引用能否在原文里找到。

默认每场只做一次判断。对重要或有争议的会议可以提交第二份判断。候选清单有差异时，看板并列显示两份结论和依据，等你选择。仅措辞不同也可能触发分歧。用 `resolve` 选定判断后再采纳条目。

第一次使用时，从一场试审开始。先看少量候选，再告诉 AI 哪类内容以后值得提醒或可以跳过。明确同意长期沿用后，AI 才会把对应规则写进本地的 `审阅偏好.md`。不同会议类型可有不同偏好。

在仓库目录运行以下命令。会议文件名可从处理页复制，示例使用虚构数据。

```bash
python3 bin/review.py --root "$MEETING_KB" status
python3 bin/review.py --root "$MEETING_KB" record '2026-11-12_1530_clipboard.txt' review.json
```

## 谁决定沉淀什么

打开处理页看判断理由和每条候选的原文。下面的命令采纳第 1 和第 3 条，其余标为未采纳。留空表示全部跳过。

```bash
python3 bin/review.py --root "$MEETING_KB" confirm '2026-11-12_1530_clipboard.txt' 1 3
```

已采纳内容写入 `knowledge/已确认/`。没有候选时，页面仍保留判断人和理由。需要正式归档和索引时，用 `archive.sh` 复制原文进 `raw/meetings/`，再跑 `reindex.py`。

## 要查东西的时候

直接问，不需要记日期：

> 上次讨论读书会安排是哪几场？
> 活动时间是怎么定的？
> 图书整理方式是什么时候变的？

以上问题均为虚构示例。

AI 去检索 `index/` 和 `raw/meetings/`，返回：日期 + 文件 + 时间码 + 原话。

## 每月一次（可选）

> 提炼最近的新会议

把新增的会并进五类资产：方法论、问题清单、事件库、未完成、决策日志。

不提炼也不影响检索——检索靠原文和索引。

## 每季度一次（可选）

> 扫一遍决策日志里「待观察」的条目，回填结果

这是让知识库真正"长"的唯一动作：

- 结果符合预期 → 改成「已验证」，这条经验可以复用
- 结果不符合 → 改成「已推翻」，写清为什么
- 还是没结果 → 保留「待观察」，别下结论

## 什么时候该删东西

- 保留处理页对应的 `inbox/` 原文，判断记录和已确认内容通过它追溯依据。
- 面试、闲聊、客户沟通：单独放，别混进会议库。
- 已经确认错误的结论：不要删，标「已推翻」并写原因——反例比正例值钱。
