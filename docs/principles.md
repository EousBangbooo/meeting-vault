# 设计原则

这份文档解释三个问题：为什么按这个结构存、为什么脚本这么笨、以及什么情况下不该用它。

## 一、为什么分"日志"和"知识"

会议日志的单位是**场**，知识库的单位是**判断**。

日志天然线性增长：开一场多一份。知识库必须收敛：同一件事被反复修正，最后剩下一条更准的。

如果只有日志，你得到的是一个越来越大的仓库；每次要用，都要重新从原文里提炼一遍。

所以这里的所有结构都在把"场"往"判断"上压：索引让你知道有哪些场，提炼让场变成结论，决策日志让结论带上结果。

## 二、为什么是五类资产

从会议里能稳定拿出来的，只有五种东西：

1. **方法论**——怎么做。出现频率最低，但寿命最长。
2. **问题清单**——反复卡在哪。用"提及该问题的会议数"排序，比凭印象排更可靠。
3. **事件库**——同类事上次怎么处理、结果如何。这是唯一能直接照抄的部分。
4. **未完成**——定了却没闭环的。价值在于提醒，不在于分析。
5. **决策日志**——当时为什么这么定、后来对不对。**只有这一类需要回填。**

前四类靠读，第五类靠等。

## 三、参数 / 方法 / 逻辑

| 层 | 例子 | 寿命 | 怎么存 |
|---|---|---|---|
| 参数 | 每周三整理一次图书 | 可随安排变化 | 一张表，带更新日期 |
| 方法 | 整理前先核对借阅登记 | 按适用条件复核 | 方法页，写清适用条件 |
| 逻辑 | 流程要服务于方便读者找到图书 | 随目标变化复核 | 原则页，定期检查 |

以上图书整理示例为虚构内容。

把参数写进方法，规则一变就要改整页；把方法当参数，会误以为"这条经验作废了"。

判断一条内容属于哪层，问一句：**换个项目、换个具体参数，它还成立吗？**

## 四、为什么要哈希

它有三个用途，一个限制：

- 去重：同一场会被复制两遍时跳过；
- 验真：文件被截断或改过时能发现；
- 挂靠：结论可以指向"哪个版本的原文"。

限制：**它不是备份。** 文件删了，指纹只剩一串数字。

## 五、为什么脚本这么"笨"

- 不解析会议软件：UI 会变，剪贴板不会。
- 不自动起标题：剪贴板里没有标题，硬猜一定错。
- 不自动提炼：判断需要上下文，脚本给不了。

**脚本只做"搬运和校验"，判断留给人和 AI。** 这条边界一破，工具就会开始制造错误的知识。

## 六、什么情况下别用

- 你的会议没有转写。先解决录音转文字，再谈归档。
- 你只需要一份好看的纪要。那是另一个问题。
- 你想全自动、零维护。任何方案都做不到，这个方案只是把维护压到每月一次。
- 你的会议内容高度敏感且不能落盘。那应该用带权限管理的系统，不是本地 txt。
