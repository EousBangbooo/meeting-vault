# Meeting Vault

把你录过的会议，变成**可检索的档案**和**可复用的知识**——而不是一堆没人再打开的纪要。

> A small, file-based toolkit for turning meeting transcripts into a searchable vault and reusable knowledge. macOS for the clipboard watcher; everything else is plain bash + Python.

---

## 问题

大多数团队的会议记录是这样死的：

1. 每场会都录，转写存成 txt 或丢进文档工具；
2. 存的时候没有命名规则，三个月后没人知道 `11.6-2.txt` 是哪场；
3. 要用的时候靠回忆和翻找，翻到了也只有原文；
4. 同一个问题在培训里讲了五遍，因为从来没有一页可查的东西；
5. 会开完了，决定做了，然后没有人回头看结果。

结果：**录音越来越多，经验没有变多。**

## 它做什么

| 能力 | 说明 |
|---|---|
| **复制即入箱** | macOS 后台监听剪贴板，识别转写格式，自动落盘并去重 |
| **会议处理页** | 在本地 HTML 看板查看未启动、等结果、待确认、判断有分歧和已处理的会议 |
| **索引与体检** | 扫描归档目录，生成索引 + 盘点报告（重复、无主题、命名不规范） |
| **提炼协议** | 由你指定的 AI 或人工提出候选，采纳后写入本地知识库 |

它**不做**：自动点击会议软件、自动转录（那是录音工具的事）、替你判断。

## 核心观点

这套东西真正的部分不是脚本，是下面四条。

### 1. 会议日志 ≠ 知识库

| | 会议日志 | 知识库 |
|---|---|---|
| 单位 | 一场会 | 一个判断 |
| 组织 | 按时间 | 按问题 |
| 增长 | 线性（+1 场） | 收敛（同一条被改得更准） |
| 读者 | 未来的你查"那天说了啥" | 现在的你问"这次怎么办" |
| 死法 | 越积越多，没人看 | 长期不更新，过期 |

绝大多数人卡在左边，然后以为自己在建右边。

### 2. 从会议里能提炼五类资产

| 资产 | 回答的问题 |
|---|---|
| 方法论 | 这件事该怎么做 |
| 问题清单 | 团队反复卡在哪（按覆盖场次排序） |
| 事件库 | 同类事上次怎么处理、结果如何 |
| 未完成事项 | 哪些事定了却没闭环 |
| 决策日志 | 当时为什么这么定、后来对不对 |

前四类从"会里说的话"提炼，第五类从"会后的结果"提炼。**只有第五类需要回填，也只有第五类能校准你的判断。**

### 3. 参数、方法、逻辑，寿命完全不同

| 层 | 例子 | 寿命 | 放哪 |
|---|---|---|---|
| 参数 | 每周三整理一次图书 | 可随安排变化 | 单独记录，标注日期 |
| 方法 | 整理前先核对借阅登记 | 按适用条件复核 | 方法页，写清适用条件 |
| 逻辑 | 流程要服务于方便读者找到图书 | 随目标变化复核 | 原则页，定期检查 |

以上是虚构的图书整理示例，不代表实际业务或通用时效。

把参数当方法沉淀，规则一变，整页作废，连里面对的方法一起丢掉——这是很多"知识库"死掉的真实原因。

### 4. 决策必须回填

决策如果没有后续结果，就很难判断当时的依据是否可靠。

因此决策日志的每条都带一个"待观察"，下次同类会议出现时先查旧的那条，把结果写回去。

## 隐私与使用边界

转写可能包含个人信息和商业秘密。可选监听器会持续读取剪贴板并把符合格式的文本保存到本地；请仅在有权处理资料的设备上使用。工具不提供加密、访问控制或备份，请保护会议库、索引及日志，切勿将真实会议数据提交到公开仓库，也不要把敏感内容发送给未经授权的 AI 服务。运行 `./bin/uninstall.sh` 可停止监听。自动识别可能漏判或误判，结果需要人工复核。

## 快速开始

无需安装 Obsidian，可用普通文本编辑器查看文件。剪贴板监听仅支持 macOS；Windows 下脚本兼容性尚未实测。

```bash
git clone https://github.com/EousBangbooo/meeting-vault.git
cd meeting-vault

export MEETING_KB="$HOME/MeetingVault"

# 1. 初始化你的会议库（默认 ~/MeetingVault，可用 MEETING_KB 覆盖）
./bin/setup.sh

# 2. macOS：安装剪贴板监听（可选，但强烈建议）
./bin/install.sh

# 3. 归档一份转写
./bin/archive.sh ~/Desktop/2026-11-12-读书会.txt

# 4. 重建索引
python3 bin/reindex.py --root "$MEETING_KB" --out "$MEETING_KB/index"
```

## 目录结构

```
$MEETING_KB/
├── 会议处理.md              状态、判断、依据、采纳结果
├── 会议处理.html            可视化计数、复制单场审阅指令
├── raw/
│   ├── meetings/            正式归档的原文
│   └── _manifest.tsv        日期 / 文件名 / SHA256 / 字数
├── inbox/                   剪贴板监听落盘区
├── index/
│   ├── 会议索引.md
│   ├── 会议索引.csv
│   └── 盘点报告.md
└── knowledge/               提炼产物（由 AI 按 docs/prompts.md 生成）
    ├── 已确认/              你确认采纳的会议判断
    ├── 方法论.md
    ├── 问题清单.md
    ├── 事件库.md
    ├── 未完成.md
    └── 决策日志.md
```

设计上刻意用**纯文件**：可以用 Obsidian、VS Code、任何编辑器打开，也能被 `git` 版本化。不引入数据库，是因为这东西的寿命要比任何一个工具都长。

## 日常流程

```
复制转写 → 已保存，等待判断（脚本保存并通知）
指定 AI 或人工 → 记录判断、原文依据和候选
你确认候选 → 已采纳条目写入 knowledge/已确认/
```

打开会议库根目录的 **会议处理.html** 看进度。展开未启动的会议，复制一条短指令发给能读本地文件的 AI。AI 只读这份转写和审阅标准，接单后登记状态。默认每场只判一次，重要会议可以按同一标准复核。两份候选有差异时由你对照原文选定。具体操作见[工作流](docs/workflow.md)。

首次使用可从一场试审开始。看过候选后，再决定哪类内容值得提醒。确认过的偏好可保存在本地 `审阅偏好.md`，以后只用于适用的会议。

## 设计取舍

**为什么不做全自动点击？**
会议软件的 UI 会变，自动化脚本三个月就废。剪贴板是唯一稳定的接口。

**为什么用哈希？**
同一场会可能被复制两遍（补录、重下一次），指纹一致就跳过。它是指纹，不是备份——文件删了它救不回来。

**为什么索引要自动生成？**
手工维护的索引一定会和文件漂移。以文件系统为唯一事实源，跑一次脚本就能重建。

**为什么区分"会议"和"面试"？**
面试记录混进会议库，可能被 AI 当作普通会议反复读取；这涉及隐私，应单独管理并人工复核分类。

## 适用 / 不适用

**适用**
- 会议频繁、有转写、需要长期回查
- 你愿意用"判断 + 依据 + 结果"的方式记录，而不是写纪要
- 接受"大部分会不产生知识"

**不适用**
- 只想要一份漂亮的会议纪要
- 没有转写来源（先解决录音转写）
- 希望全自动、零维护（任何方案都做不到）
